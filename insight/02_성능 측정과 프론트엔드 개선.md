# 02. 성능 측정과 프론트엔드 개선

## 복잡도 분석과 성능 측정의 차이

- **복잡도 분석**: 코드가 데이터 증가에 따라 얼마나 많은 작업·메모리를 요구하는지 판단합니다.
- **성능 측정**: 실제로 실행해서 걸린 시간과 메모리 사용을 확인합니다.
- 개선 순서: **느린 현상 확인 → 측정 → 원인 파악 → 수정 → 같은 조건으로 재측정**.

## 함수 실행 시간 재기

solution 함수와 입력을 준비한 뒤, 브라우저에서 아래 코드를 실행합니다.

```javascript
const start = performance.now();
const result = solution(participant, completion);
const elapsed = performance.now() - start;

console.log(result);
console.log(`${elapsed.toFixed(2)}ms`);
```

- `performance.now()`: 시간 측정용 숫자를 밀리초 단위로 반환합니다. 실행 전후 차이가 걸린 시간입니다.
- `toFixed(2)`: 소수점 둘째 자리까지 표시합니다. 측정 정확도가 높아지는 것은 아닙니다.
- 이 코드는 **동기 함수**용입니다. 비동기 함수가 끝날 때까지 측정하려면 async 함수 안에서 `await solution(...)`으로 기다려야 합니다.
- 입력 생성·콘솔 출력은 측정 구간 밖에 두고, 결과가 맞는지 먼저 확인합니다.
- 같은 환경·입력으로 몇 번 예열한 뒤 여러 번 측정합니다. 한 번의 결과보다 중앙값과 편차를 봅니다.
- 1천·1만·10만 건처럼 입력 크기를 바꿔 증가 추세도 확인합니다. 원본을 수정하는 풀이는 매번 동일한 내용의 새 입력을 준비합니다.

## 화면이 느릴 때 확인할 곳

- **Performance**: 느린 클릭·스크롤 구간을 녹화해서 긴 JavaScript 실행, 화면 배치 계산·그리기 비용을 확인합니다.
- **Network**: 요청 시간·크기·중복 요청을 확인합니다. 느린 서버 응답은 반복문을 고친다고 해결되지 않습니다.
- **Memory**: 같은 동작을 반복할 때 메모리가 계속 남는지 확인합니다. 일시적인 증가는 곧바로 누수를 뜻하지 않습니다.

## 원인에 따른 개선 예시

- **반복 계산**: 매번 배열 전체를 검색한다면, 이름별 조회 객체·Map을 미리 만드는 방식을 비교합니다.
- **너무 많은 화면 요소**: 목록에 수만 개 DOM을 만들고 있다면 페이지 분할이나 화면에 보이는 부분만 그리는 방식을 검토합니다.
- **과도한 요청**: 검색어 한 글자마다 요청한다면 잠시 입력이 멈춘 뒤 요청하는 디바운스를 검토합니다.
- **큰 파일**: 이미지 크기·형식과 불필요하게 처음부터 불러오는 코드를 확인합니다.
- **메모리 누적**: 화면을 떠날 때 이벤트 리스너·타이머 등을 적절히 해제했는지 확인합니다.
- 원인이 확인된 부분부터 바꿉니다. Map·캐시를 추가하면 오히려 메모리나 관리 비용이 늘 수도 있습니다.

## 포트폴리오 기록 방법

- **현상**: 어떤 화면·동작이 느렸는지.
- **조건**: 데이터 건수, 브라우저·기기, 측정 방법과 반복 횟수.
- **원인·수정**: 측정으로 찾은 원인과 바꾼 코드.
- **결과**: 실제 측정한 수정 전후 수치, 정상 동작 확인, 메모리 등 다른 비용의 변화.
- 예시 틀: ‘가상 데이터 ___건에서 검색 처리 중앙값 ___ms → ___ms. 변경 내용: ___. 검증: ___.’
- 측정하지 않은 숫자는 만들지 않습니다. 개인 프로젝트 실험과 회사 실무 성과를 구분합니다.

**핵심: “빠른 문법을 썼다”가 아니라 “느린 원인을 찾고, 수정한 뒤 개선을 확인했다.”**
